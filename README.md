# TG.MaxDirectBot

`TG.MaxDirectBot` — мост между личными сообщениями Telegram Business и одним
оператором в мессенджере MAX. Новое обращение из разрешённого личного чата
Telegram приходит оператору в MAX. Оператор использует обычную функцию
**«Ответить»** на карточке сообщения, после чего ответ отправляется в правильный
диалог Telegram от имени подключённого Telegram-аккаунта.

Проект использует только официальные Bot API Telegram и MAX. Авторизация под
обычным пользовательским аккаунтом, чтение локальной базы Telegram, эмуляция
клиента и browser automation не нужны.

## Как это работает

```text
Клиент пишет в личку Telegram
              ↓
Telegram Business Bot → polling/webhook → TG.MaxDirectBot → бот MAX → оператор
              ↑                                             ↓
              └──────── ответ через Business connection ────┘
```

1. Приложение получает `business_message` через long polling либо защищённый webhook.
2. Событие сохраняется в SQLite до обработки.
3. Фоновый обработчик пересылает сообщение оператору в MAX и сохраняет связь:
   `ID сообщения MAX → business_connection_id + чат + сообщение Telegram`.
4. Оператор нажимает **«Ответить»** на карточке в MAX.
5. По ID связанного сообщения приложение находит исходный Telegram-диалог и
   вызывает Telegram Bot API с `business_connection_id`.
6. Клиент видит ответ от исходного Telegram-аккаунта. Telegram при этом хранит
   технический признак отправки через подключённого Business-бота.

## Возможности

- пересылка входящих личных сообщений Telegram Business одному оператору MAX;
- точная маршрутизация ответа через штатный reply в MAX;
- текст, фотографии, видео, аудио и обычные файлы в обе стороны;
- разбиение длинного входящего текста без потери содержимого;
- игнорирование исходящих сообщений владельца Telegram и защита от циклов;
- жёсткое ограничение ответов по `MAX_OPERATOR_USER_ID`;
- проверка секретов в заголовках Telegram и MAX webhook;
- очередь событий в SQLite, повтор обработки после временной ошибки API;
- дедупликация повторно доставленных webhook;
- бездоменный long polling одновременно для Telegram и MAX;
- сохранение Telegram offset и MAX marker в SQLite между перезапусками;
- ограничение скорости отправки в MAX до двух сообщений в секунду;
- автоматический HTTPS через Caddy и запуск одной командой Docker Compose;
- CLI для проверки токенов и настройки обоих webhook;
- healthcheck `/healthz` и тесты основных сценариев.

## Важные ограничения

- К Telegram-аккаунту одновременно подключается только один Business-бот.
- Бот получает только те личные чаты, которые разрешены в настройках подключения
  Telegram. Секретные чаты не поддерживаются.
- Ответ приходит от того Telegram-аккаунта, к которому подключён бот. Если
  оператором является другой человек, его личный Telegram-профиль клиенту не
  показывается.
- Для создания бота MAX нужен верифицированный профиль организации, ИП или
  самозанятого — резидента РФ. Бот должен пройти модерацию.
- MAX рекомендует webhook для production. Polling предназначен прежде всего для
  разработки, первичного теста и небольших внутренних установок.
- Стикеры, реакции, опросы, геопозиции, контакты, редактирование и удаление
  сообщений пока передаются только текстовой пометкой или не синхронизируются.
- Облачный Telegram Bot API ограничивает скачивание файлов. Дополнительно проект
  по умолчанию ограничивает перенос размером `20 МБ`; лимит можно изменить через
  `MAX_DOWNLOAD_BYTES`, но фактические ограничения платформ останутся.
- SQLite и локальный ограничитель скорости рассчитаны на один экземпляр
  приложения. Не запускайте несколько реплик без переноса очереди и rate limit в
  общий Redis/PostgreSQL.
- Доставка имеет семантику «как минимум один раз». Дедупликация закрывает обычные
  повторы webhook, но при аварийном завершении между внешним API-запросом и
  фиксацией результата теоретически возможно повторное сообщение.

## Что понадобится

- для polling: сервер с исходящим интернетом и Python 3.9+, домен не нужен;
- для production webhook: публичный домен, HTTPS и порт 443;
- Docker необязателен: поддерживаются обычный `.venv` + systemd и контейнер;
- Telegram-бот, созданный через `@BotFather`;
- бот MAX, созданный и прошедший модерацию на платформе MAX для партнёров;
- числовой MAX ID оператора;
- отдельный Telegram-аккаунт для рекламных обращений либо тщательно настроенный
  список разрешённых и исключённых личных чатов.

Рекомендуется использовать отдельный Telegram-аккаунт для рекламы. Режим
`All Private Chats Except…` на основном личном аккаунте может передать мосту
переписку, которую вы не собирались показывать оператору или хранить на сервере.

## 1. Создание Telegram-бота

1. Откройте `@BotFather` в Telegram.
2. Создайте бота командой `/newbot` и сохраните токен.
3. В настройках бота включите **Business Mode**.
4. Пока не подключайте webhook вручную — это сделает CLI проекта.

После запуска сервиса подключите бота к аккаунту, принимающему обращения:

1. Telegram → **Настройки** → **Telegram Business** → **Чат-боты**.
2. Укажите username созданного бота.
3. Разрешите боту отвечать на сообщения.
4. Выберите `Only Selected Chats` либо настройте исключения для личных чатов.

Для автоматической обработки всех новых рекламных обращений удобнее отдельный
Telegram-аккаунт и режим всех личных чатов с минимальным числом исключений.

## 2. Создание бота MAX

На момент подготовки проекта бот MAX создаётся только для верифицированного
профиля организации, ИП или самозанятого — резидента РФ.

1. Откройте платформу **MAX для партнёров** или мини-приложение
   **«MAX для бизнеса»**.
2. Создайте и верифицируйте профиль.
3. Создайте чат-бота и отправьте его на модерацию.
4. После успешной проверки откройте **Расширенные настройки → Настроить** и
   скопируйте токен.
5. Оператор должен открыть этого бота в MAX и нажать **«Начать»**. До этого бот
   обычно не сможет первым отправить ему личное сообщение.

## 3. Как узнать `MAX_OPERATOR_USER_ID`

Самый надёжный способ на первом запуске:

1. временно настроить webhook или long polling по документации MAX;
2. написать боту из аккаунта оператора;
3. взять число из `message.sender.user_id` события `message_created`.

В рабочем `.env` должен быть именно числовой ID пользователя, а не ник, телефон
или `chat_id` группового чата. Приложение принимает ответы только от этого ID.

## 4. Установка на сервер

```bash
git clone https://github.com/dvygolov/TG.MaxDirectBot.git
cd TG.MaxDirectBot
cp .env.example .env
```

### Вариант A: без домена, polling + systemd

Для первичной проверки достаточно:

```dotenv
UPDATE_MODE=polling
TELEGRAM_BOT_TOKEN=123456789:...
MAX_BOT_TOKEN=...
MAX_OPERATOR_USER_ID=123456789
DATABASE_PATH=data/bridge.db
POLLING_TIMEOUT_SECONDS=50
```

Установка отдельного окружения и сервиса:

```bash
chmod +x build.sh install-service.sh update.sh
./build.sh
./install-service.sh
systemctl status tg-maxdirectbot.service
journalctl -u tg-maxdirectbot.service -f
```

При старте polling-режим отключает Telegram webhook и удаляет активные webhook-
подписки MAX, поскольку обе платформы не позволяют использовать webhook и long
polling одновременно. Offset Telegram и marker MAX сохраняются в SQLite.

Если Business Mode Telegram-бота ещё не включён, сервис стартует с предупреждением
и продолжает опрашивать обе платформы. После включения режима в `@BotFather`
перезапуск обычно не требуется.

Обновление:

```bash
./update.sh
```

### Вариант B: production webhook + Docker/Caddy

Сгенерируйте два независимых секрета webhook:

```bash
python -c "import secrets; print(secrets.token_urlsafe(32))"
python -c "import secrets; print(secrets.token_urlsafe(32))"
```

Заполните `.env`:

```dotenv
PUBLIC_BASE_URL=https://bot.example.ru
DOMAIN=bot.example.ru
UPDATE_MODE=webhook

TELEGRAM_BOT_TOKEN=123456789:...
TELEGRAM_WEBHOOK_SECRET=...

MAX_BOT_TOKEN=...
MAX_OPERATOR_USER_ID=123456789
MAX_WEBHOOK_SECRET=...

DATABASE_PATH=/app/data/bridge.db
```

Создайте DNS-запись `A`/`AAAA` домена на сервер. Затем запустите контейнеры:

```bash
docker compose up -d --build
docker compose ps
docker compose logs -f app
```

Caddy автоматически получает обычный публично доверенный TLS-сертификат и
проксирует HTTPS-запросы приложению. MAX принимает webhook только по HTTPS на
порту 443 и не принимает самоподписанный сертификат.

Если на сервере уже есть Nginx, Caddy или другая ingress-система, можно запустить
только контейнер `app` и направить два URL на порт 8000:

- `POST /webhooks/telegram`;
- `POST /webhooks/max`.

Не публикуйте порт 8000 напрямую в интернет без обратного прокси и HTTPS.

## 5. Сертификат для исходящих запросов MAX

Актуальная документация MAX требует обращаться к
`https://platform-api2.max.ru` и убедиться, что сертификат Минцифры добавлен в
доверенные. Проверка TLS в проекте никогда не отключается.

Если системного набора CA на вашем сервере достаточно, ничего менять не нужно.
Если при `check` появляется ошибка проверки сертификата:

1. получите актуальный корневой сертификат только из официального источника;
2. сохраните его, например, как `certs/russian_trusted_root_ca.pem`;
3. раскомментируйте в `.env`:

```dotenv
MAX_CA_FILE=/app/certs/russian_trusted_root_ca.pem
```

4. перезапустите приложение: `docker compose up -d --build app`.

Не используйте `verify=False` и не загружайте случайный сертификат из
неофициального репозитория.

## 6. Проверка токенов и регистрация webhook

Проверить токены, Business Mode и текущие подписки:

```bash
docker compose exec app tg-max-direct-bot check
```

Зарегистрировать оба webhook:

```bash
docker compose exec app tg-max-direct-bot setup-webhooks
```

Для polling регистрировать webhook не нужно. Запуск вручную:

```bash
UPDATE_MODE=polling tg-max-direct-bot run-polling
```

Команда:

- проверяет, что Telegram-бот имеет `can_connect_to_business`;
- устанавливает Telegram webhook с секретным заголовком;
- подписывает MAX на `message_created` и `bot_started`;
- передаёт MAX отдельный webhook-secret;
- при повторном запуске заменяет подписку проекта на тот же URL.

Проверка доступности приложения:

```bash
curl -fsS https://bot.example.ru/healthz
```

Ожидаемый ответ:

```json
{"status":"ok"}
```

## 7. Проверка полного сценария

1. В MAX откройте бота оператором и нажмите **«Начать»**.
2. Подключите Telegram Business-бота к нужному аккаунту и разрешите ему отвечать.
3. С другого Telegram-аккаунта отправьте тестовое сообщение в личку.
4. Убедитесь, что в MAX появилась карточка с именем, Telegram ID и текстом.
5. В MAX нажмите **«Ответить»** именно на эту карточку.
6. Напишите ответ.
7. Убедитесь, что ответ появился в исходном Telegram-диалоге от имени
   подключённого аккаунта.

Если просто написать боту MAX отдельное сообщение, он попросит использовать
функцию **«Ответить»** — без связи с карточкой невозможно безопасно определить
нужного Telegram-получателя.

## Переменные окружения

| Переменная | Обязательна | Назначение |
|---|---:|---|
| `UPDATE_MODE` | нет | `polling` без домена или `webhook`; по умолчанию `webhook` |
| `PUBLIC_BASE_URL` | для webhook | Публичный HTTPS URL без завершающего `/` |
| `DOMAIN` | для Caddy | Домен, на который Caddy получает сертификат |
| `TELEGRAM_BOT_TOKEN` | да | Токен из `@BotFather` |
| `TELEGRAM_WEBHOOK_SECRET` | для webhook | Секрет заголовка Telegram webhook |
| `MAX_BOT_TOKEN` | да | Токен прошедшего модерацию бота MAX |
| `MAX_OPERATOR_USER_ID` | да | Единственный MAX user ID, которому разрешено отвечать |
| `MAX_WEBHOOK_SECRET` | для webhook | Секрет заголовка MAX webhook |
| `DATABASE_PATH` | нет | SQLite, по умолчанию `data/bridge.db` |
| `LOG_LEVEL` | нет | `INFO`, `WARNING`, `DEBUG` и т. п. |
| `HTTP_TIMEOUT_SECONDS` | нет | Тайм-аут внешних API, по умолчанию 30 секунд |
| `POLLING_TIMEOUT_SECONDS` | нет | Тайм-аут long polling, 1–90 секунд; по умолчанию 50 |
| `POLLING_DROP_PENDING_UPDATES` | нет | Удалить старые Telegram updates при первом переключении |
| `MAX_DOWNLOAD_BYTES` | нет | Лимит переносимого файла, по умолчанию 20 МБ |
| `SEND_CONFIRMATIONS` | нет | Отправлять в MAX подтверждение успешного ответа |
| `MAX_CA_FILE` | нет | Дополнительный доверенный CA-файл для API MAX |

Секреты должны содержать 5–256 символов `A-Z`, `a-z`, `0-9`, `_` или `-`.

## Работа с очередью и данными

Webhook и polling используют одну очередь. Событие сначала записывается в
SQLite. Фоновый обработчик выполняет
перенос и при временной ошибке повторяет попытку с увеличивающимся интервалом до
пяти минут. Незавершённые события восстанавливаются после перезапуска.

В `data/bridge.db` хранятся:

- служебные webhook-события;
- ID Telegram Business connection;
- соответствия ID сообщений MAX и Telegram;
- технические ошибки повторных попыток.
- Telegram polling offset и MAX polling marker.

Успешно обработанные события очереди автоматически удаляются через семь дней
при следующем запуске. Сама переписка может оставаться в таблице событий до этой
очистки, поэтому защищайте каталог `data/` и учитывайте требования к персональным
данным. Таблица соответствий хранится дольше, чтобы оператор мог ответить на
старую карточку после перезапуска.

Резервная копия:

```bash
docker compose stop app
cp data/bridge.db data/bridge.db.backup
docker compose start app
```

## Локальная разработка

Требуется Python 3.9 или новее:

```bash
python -m venv .venv
source .venv/bin/activate
pip install -e ".[dev]"
cp .env.example .env
pytest
ruff check .
```

В PowerShell активация окружения выполняется так:

```powershell
.venv\Scripts\Activate.ps1
```

Для локального polling публичный endpoint не нужен. Для webhook нужен HTTPS.
Production-документация MAX рекомендует webhook; polling оставлен как удобный
режим первоначальной проверки и небольшого внутреннего развёртывания.

## Диагностика

### В MAX ничего не приходит

- оператор не нажал **«Начать»** у бота MAX;
- неверно указан `MAX_OPERATOR_USER_ID`;
- MAX-бот ещё не прошёл модерацию;
- подписка не создана — запустите `tg-max-direct-bot check`;
- endpoint недоступен по HTTPS:443 или цепочка сертификата неполная;
- API MAX не проходит TLS-проверку — проверьте раздел про `MAX_CA_FILE`;
- Telegram Business-боту не разрешён нужный личный чат.

### Ответ из MAX не уходит

- использовано новое сообщение вместо функции **«Ответить»**;
- ответ отправляет пользователь с другим MAX ID;
- Telegram Business connection отключён или не имеет права отвечать;
- карточка создана другой установкой, а её соответствия нет в текущей SQLite;
- вложение превышает лимит или его формат не поддерживается платформой.

### Telegram-бот нельзя подключить к аккаунту

Включите Business Mode в `@BotFather` и убедитесь через
`tg-max-direct-bot check`, что API возвращает `business=True`.

### Посмотреть журналы

```bash
docker compose logs --tail=200 app
docker compose logs -f app
```

При установке через systemd:

```bash
journalctl -u tg-maxdirectbot.service --since today
journalctl -u tg-maxdirectbot.service -f
```

Токены намеренно не выводятся в журнал. Не публикуйте логи, если в них есть имена,
Telegram ID или содержимое обращений.

## Обновление

```bash
git pull --ff-only
docker compose up -d --build
docker compose exec app tg-max-direct-bot check
```

Для systemd-установки: `./update.sh`.

Перед крупным обновлением сделайте резервную копию `data/bridge.db`.

## Безопасность

- `.env`, SQLite, сертификаты и токены исключены из Git;
- оба webhook проверяются через независимые секретные заголовки;
- ответы разрешены только одному `MAX_OPERATOR_USER_ID`;
- TLS-проверка внешних API не отключается;
- вложения ограничены по объёму;
- приложение в контейнере работает не от root;
- FastAPI Swagger/ReDoc отключены в production-приложении.

Дополнительные рекомендации находятся в [SECURITY.md](SECURITY.md).
